## 项目概览

这是一个在浏览器中重建《原神》启动演出的 WebGL 实验。体验从资源加载和登录界面开始，随后进入云海飞行，沿天空道路经过漂浮遗迹，等待天空之门生成，最后冲入门内并以白光完成转场。

项目的重点不是复刻一张静态画面，而是把模型、Shader、镜头、音频、UI 和交互组织成一段连续、可恢复、可销毁的实时演出。原始场景代码被重新整理为 TypeScript 模块，并接入 Astro 的页面生命周期，使它能够稳定运行在个人网站而不是孤立的 WebGL Demo 中。

> 本项目为非商业技术复刻，仅用于 WebGL 学习、研究和技术展示，与 HoYoverse 或米哈游无关联。

## 技术栈

| 模块     | 技术                         | 用途                                   |
| -------- | ---------------------------- | -------------------------------------- |
| 实时渲染 | WebGL、Three.js、xviewer     | 场景图、相机、模型、动画与渲染循环     |
| 视觉效果 | GLSL、ShaderMaterial         | 云层、极光、星光、雾效与 Toon 光照     |
| 性能优化 | InstancedMesh、对象循环复用  | 批量绘制遗迹、云层与光柱，维持连续飞行 |
| 后处理   | FXAA、Bloom、ACES Filmic     | 抗锯齿、辉光、色调映射与入门白光转场   |
| 交互编排 | TypeScript、事件系统、状态机 | 管理加载、启动、飞行、门生成和完成状态 |
| 页面集成 | Astro、动态导入              | 沉浸式界面、按需初始化与离场资源回收   |

## 体验流程

整个项目按一条明确的演出链路运行：

```text
加载模型与纹理
  → 显示登录界面
  → 用户启动
  → 镜头穿越云海与遗迹
  → 道路停止并生成天空之门
  → 用户点击进入
  → 开门、镜头加速、Bloom 白光
  → 演出完成或重新开始
```

每个阶段都由事件驱动，而不是依赖散落在不同组件里的固定延时。场景组件发出 `showDoor`、`doorCreate` 等领域事件，控制器再把它们转换成页面可理解的 `portal-ready`、`whiteout` 和 `complete` 状态。

## 系统架构

### 控制器与渲染核心

`GenshinController` 是 Astro 页面和 WebGL 核心之间的边界。页面只调用初始化、启动、进入门、静音和销毁等少量方法，不直接操作 Three.js 对象。

```text
Astro UI
  └─ GenshinController
       ├─ Game
       │    ├─ Viewer
       │    ├─ StateMachine
       │    └─ Scene Components
       └─ GameManager / EventEmitter
```

`Game` 负责资源预加载、场景创建、演出启动、音频和最终白光转场；场景中的道路、相机、云层、遗迹、光柱和门则分别实现为组件。组件之间通过 `GameManager` 的事件系统通信，减少相互引用。

### 状态管理

渲染核心使用状态机保证“预加载完成后才能创建场景”，页面控制器则维护更细的体验状态：

```text
idle → loading → ready → flying
     → portal-forming → portal-ready
     → entering → complete
```

按钮是否可用、天空之门入口是否显示、失败后是否允许重试，都由当前状态决定。重复点击启动或进入按钮不会再次触发同一段演出。

## 资源加载

所有 GLB、纹理、音频和 UI 路径统一收敛到资源清单中，避免组件内部散落硬编码 URL。模型和材质纹理通过 Promise 并行预加载，`TaskManager` 根据已完成任务的权重汇总进度，再把结果同步给加载界面。

渲染控制器通过动态 `import()` 进入页面后才加载，WebGL 代码不会进入普通内容页面的首屏执行路径。加载失败会切换到独立错误状态，访客可以直接重试而无需刷新整站。

音频只在用户主动点击启动后播放，以符合浏览器自动播放策略；音效播放失败不会阻塞主演出。

## 场景构建

### 连续前进的天空道路

相机以固定速度沿 Z 轴向前移动。道路由多个单元首尾拼接，当一个单元越过相机后，会被移动到队列末端并重新播放出现动画。这个循环复用机制制造了持续前进的感觉，同时避免无限创建几何体。

达到预设节点后，道路停止循环并触发天空之门生成。门的 GLB 动画由 `AnimationMixer` 驱动，门体动画结束后才将入口标记为可点击。

### 实例化遗迹、云层与极光

重复出现的柱体、桥梁、平面云和极光使用 `InstancedMesh` 合并绘制。每个实例的位置、旋转和缩放由配置数据写入矩阵；当它越过镜头后，只更新实例矩阵并移动到远端重新参与循环。

相比为每个对象创建独立 Mesh，实例化显著减少了重复遗迹和特效产生的 draw call，是浏览器端保持稳定帧率的关键。

### 相机与镜头节奏

`ForwardCamera` 在飞行阶段持续更新相机中心。出现天空之门后，相机通过 Cubic Out 缓动减速并停在门前；用户确认进入后，旧 Tween 被取消，相机改用 Cubic In 加速穿门。场景物体围绕相机中心循环，使有限长度的内容产生更长的空间旅程。

## Shader 与材质

项目没有只依赖标准 PBR 材质，而是针对不同层次编写和注入 Shader：

- 平面云通过遮罩纹理和透明混合形成远近云层；
- 大云层始终跟随相机，维持远景包围感；
- Hash Fog 使用时间 uniform 生成动态雾效；
- 极光纹理沿 UV 流动，并与星光粒子共同构成高空光带；
- 道路、柱体和门通过 `onBeforeCompile` 替换 Three.js 光照片段，加入 Toon 明暗和 Fresnel 边缘光；
- 材质关闭不必要的深度写入，并为道路纹理设置各向异性过滤，降低斜视角模糊。

这种拆分让不同视觉层能够独立更新，也保留了标准 Three.js 材质的模型、贴图和灯光能力。

## 后处理与入门转场

基础画面依次经过 FXAA、Bloom 和 ACES Filmic 色调映射。Bloom 只强化高亮区域，使天空之门和极光获得发光感，同时避免整个画面泛白。

进入门时，自定义后处理效果会先提升亮度，再把画面逐渐混合到纯白。这个过程和相机加速、开门动画、穿门音效共享同一条时间线，从而把 3D 场景自然衔接到完成界面，而不是直接切换 DOM。

## 页面集成与资源回收

沉浸式场景运行在 Astro 页面中，因此需要处理单页导航带来的生命周期问题：

- 页面加载时动态创建控制器和 WebGL Viewer；
- `ResizeObserver` 根据容器尺寸更新画布和相机；
- 重试或重播前先销毁当前实例，再执行完整初始化；
- 离开页面时停止渲染循环和未完成的计时器；
- 解绑全局事件、清空状态机和事件总线；
- 停止音频并移除音频资源；
- 销毁 Viewer，释放场景、材质、纹理和 WebGL 上下文。

这样可以避免访客返回项目列表后背景音乐仍然播放，也避免多次进入体验页产生重复监听器或多个渲染循环。

## 实现难点

### 把视觉脚本变成可维护的演出系统

原始 Demo 的画面逻辑分布在模型、组件和事件回调中。重构时保留了场景表现，同时增加统一控制器、明确的状态流和资源清单，使页面 UI 不再依赖底层对象的内部实现。

### 无限场景与有限资源

天空道路和遗迹需要让用户感到一直向前，但浏览器不能无限增加对象。项目采用“越过相机后移回远端”的循环队列策略，并配合实例化绘制，在固定资源规模下维持连续空间。

### WebGL 与页面导航共存

普通网页的页面切换不会自动处理 GPU、音频和事件总线。项目将清理逻辑集中到 `destroy()`，并在 Astro 的页面切换事件触发时调用，确保每一次初始化都有对应的回收路径。

## 当前结果与局限

项目已经完整串联加载、登录、云海飞行、门生成、入门白光和重播流程，并支持静音、横屏提示、失败重试和中英文界面。

当前版本优先还原桌面端构图和演出节奏，移动设备主要提供横屏提示，尚未根据 GPU 能力动态调整实例数量、Shader 复杂度或后处理质量。后续可以加入自动画质分级、低性能降级模式和更细粒度的资源缓存策略。
