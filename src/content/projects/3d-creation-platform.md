## 项目背景与我的职责

这是一个工作项目的匿名技术案例。平台面向 AI 驱动的三维内容创作：用户在高斯场景中放置角色与道具、绑定动作、调整构图，再通过截图与 AI 图像增强获得内容。随着能力被多个业务使用，系统需要同时处理三维编辑、异步资产生成和跨产品复用。

我担任项目技术负责人，以前端为主推进核心建设，负责内部 SDK 架构、关键技术方案、跨团队协作和功能交付；同时使用 Java 扩展后端接口参数，迭代任务处理流程中的业务功能。

这项工作的重点，是把场景、角色、道具、动作和输出能力组织成能够持续扩展的创作框架。

## 可复用的三维创作框架

不同业务需要的界面与流程有所不同，但它们都依赖相近的底层能力：加载场景、放置资产、绑定动作、编辑选中状态、输出截图，以及管理资产生成任务。

我将这些通用能力沉淀为内部 SDK，让产品可以围绕自身的创作流程组织界面，并复用三维能力。上方示意图按职责概括了产品接入、编辑交互、资产任务与渲染之间的关系。

| 能力     | 承担的工作                                             |
| -------- | ------------------------------------------------------ |
| 三维编辑 | 角色与道具放置、动作绑定、选中高亮与截图               |
| 资产任务 | 场景、角色、道具、动作的生成进度、轮询、重试与资产管理 |
| 混合渲染 | 高斯场景与 Mesh 的单位、矩阵、加载及切换               |
| 产品接入 | 复用内部 SDK，结合各产品的业务界面与创作流程           |

这种组织方式使新业务能够复用已有能力，也让资产或渲染侧的改进能够集中交付。

## 统一资产生成与任务状态

场景、角色、道具和动作虽然属于不同资产类型，但生成流程都涉及任务提交、异步等待、进度展示、失败重试和结果进入资产库。如果每类资产分别实现一套流程，新增类型时就会重复处理这些问题。

我主导统一资产生成体系，将任务轮询、进度、重试及公私库管理收敛到共同的任务与资产状态体系中。不同资产保留各自的业务参数与结果处理，公共流程可以复用，界面也能以一致方式展示生成状态。

这次重构同时涉及任务调度与资产状态域。Java 侧的工作主要是接口参数扩展与任务流程迭代，与前端任务链路配合交付。

## 高斯场景与 Mesh 混合编辑

### 单位与矩阵一致性

高斯场景、传统模型和编辑器交互需要使用一致的空间约定。单位或矩阵处理不一致时，模型的尺寸、位置和编辑结果就可能出现偏差。

我处理 Gaussian Splatting 与 Mesh 的混合渲染适配，包括毫米 / 米单位自适应与矩阵缩放，使不同来源的资源能够在同一创作场景中正确组合，为角色放置、道具编辑和截图提供基础。

### 大体积 SPZ 场景切换

SPZ 场景的下载和初始化需要时间。如果在新场景准备好之前清空当前画面，切换过程就会出现黑屏或闪烁；加载失败也会使用户失去当前可用场景。

切换采用双场景叠加：加载过程中保留当前画面，在新资源准备完成后执行原子替换，失败时回滚并保留可用状态。这使异步资源加载与用户正在操作的画面能够衔接起来，解决大体积 SPZ 切换时的黑屏闪烁问题。

这里的取舍是过渡期间需要容纳新旧场景，资源释放与替换时机因此成为方案的一部分。

## 从编辑到图像输出

创作流程需要将场景、角色和动作转化为可继续使用的图像。我参与建设截图与 AI 增强链路，包括前景 Mask 离屏渲染、多分辨率输出，以及编辑时的选中高亮，让编辑状态和最终输出各自满足使用场景。

这部分与资产生成、场景加载一起组成完整的创作流程：生成和选择资产，进入三维场景完成编排，再输出图像并进入后续内容处理。

## 结果与工程体会

项目目前形成了服务 **5+ 产品线**的通用三维创作框架；统一任务与资产状态体系后，新增资产类型的开发成本降低约 **60%**。混合渲染适配与场景切换方案则解决了资源组合和切换过程中的具体体验问题。

在这个过程中，我也推进状态域重构和核心工具单测建设。对复杂工具平台而言，渲染、编辑交互与异步任务需要共同设计：任务状态决定资产何时可用，资源状态影响场景能否安全切换，而统一的能力边界决定后续业务能否复用。
