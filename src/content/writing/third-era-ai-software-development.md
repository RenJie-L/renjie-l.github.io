> 参考：[The Third Era of AI Software Development](https://cursor.com/cn/blog/third-era)

AI 对软件开发的影响，正在从「提高编码效率」逐渐走向「改变软件生产方式」。

过去几年，我们经历了代码补全、对话式编程、Coding Agent。随着 Agent 能够在独立环境中持续运行、调用工具并完成越来越长的任务，软件开发正在进入一个新的阶段：

**开发者不再需要亲自完成每一行代码，而是逐渐转向定义问题、调度 Agent 和验收结果。**

Cursor 将这一变化概括为 AI 软件开发的三个时代。

## 一、AI 软件开发的三个时代

### 1. Tab 时代：AI 帮你写代码

第一阶段的代表是代码补全。

开发者仍然掌握完整的开发流程：

```text
理解需求
  ↓
设计方案
  ↓
编写代码
  ↓
AI 补全局部代码
  ↓
调试 / 测试
  ↓
提交
```

AI 最擅长处理的是那些**低熵、重复、局部且容易预测的编码任务**。

例如：

- 补全函数实现；
- 生成重复代码；
- 根据上下文预测下一段代码；
- 完成简单的重构；
- 生成测试模板。

这一阶段本质上没有改变软件开发的生产方式。

AI 是一个更聪明的编辑器功能，而开发者仍然是代码的主要生产者。

---

### 2. Agent 时代：AI 开始完成任务

随着模型推理能力、上下文窗口和工具调用能力提升，AI 开始从「补全代码」变成「完成任务」。

开发者可以直接描述目标：

```text
修复这个 Bug
增加一个接口
重构这个模块
给这个功能补测试
```

Agent 会自己：

1. 阅读代码；
2. 搜索项目；
3. 修改多个文件；
4. 执行命令；
5. 运行测试；
6. 根据结果继续修改。

工作流逐渐变成：

```text
开发者提出任务
      ↓
Agent 分析代码
      ↓
Agent 修改代码
      ↓
Agent 执行测试
      ↓
开发者 Review
      ↓
反馈 / 继续修改
```

开发者开始从「代码生产者」转向「任务定义者」。

但这个阶段仍然有一个明显限制：

**人和 Agent 基本处于同步工作状态。**

Agent 工作几分钟后，人需要检查结果、补充信息，再继续下一轮。

所以它仍然是一种：

> Prompt → Response → Review → Prompt

的交互循环。

---

### 3. 云端自治 Agent：从协作变成调度

第三个阶段的变化，在于 Agent 开始脱离开发者的实时控制。

Agent 可以运行在独立的云端环境中，获得：

- 独立 VM；
- 完整代码仓库；
- Shell；
- 浏览器；
- 测试环境；
- 日志系统；
- CI；
- 各类内部工具。

开发者提交任务之后，Agent 可以持续运行几十分钟甚至更长时间。

于是工作流开始变成：

```text
                 ┌─ Agent A → Feature A
                 │
Developer ───────┼─ Agent B → Bug Fix
                 │
                 ├─ Agent C → Tests
                 │
                 └─ Agent D → Refactor
                        ↓
                  Results / Artifacts
                        ↓
                     Review
```

这时候真正发生变化的不是 Agent「又聪明了一点」，而是：

**开发从串行的人机协作，开始变成并行的软件生产流水线。**

Cursor 给出的数据也能看到这种趋势：

- 过去一年 Agent 使用量增长超过 **15 倍**；
- 用户行为从「Tab 用户数量约为 Agent 用户的 2.5 倍」，反转为「Agent 用户约为 Tab 用户的 2 倍」；
- Cursor 内部已经有约 **35% 的 PR** 由云端自治 Agent 产生。

软件开发的核心交互正在从：

```text
Human → Code
```

逐渐变成：

```text
Human → Agent → Code
```

甚至进一步变成：

```text
Human
  ↓
Task Graph
  ↓
Agent A ─┐
Agent B ─┼→ Code / Test / Artifact → Review
Agent C ─┤
Agent D ─┘
```

## 二、开发者的工作正在发生什么变化？

当 Agent 可以承担越来越多实现工作之后，开发者的时间分配也会随之变化。

以前大量时间花在：

- 写业务代码；
- 查 API；
- 修改类型错误；
- 写重复逻辑；
- 补测试；
- 调试简单问题。

这些工作不会完全消失，但其中很大一部分可以逐渐交给 Agent。

开发者需要投入更多精力到另外几个环节。

### 1. 问题定义

Agent 很擅长解决明确的问题，但不擅长替你决定「真正应该解决什么」。

例如：

```text
优化用户系统
```

对于 Agent 来说几乎没有可执行性。

而：

```text
目标：
减少登录接口 P95 延迟。

当前：
P95 ≈ 850ms

目标：
P95 < 300ms

约束：
- 不修改客户端协议
- 不改变数据库 Schema
- 保持现有测试通过

验收：
- benchmark 输出
- 单元测试通过
- 给出性能变化说明
```

就是一个明显更适合 Agent 的任务。

因此，**需求拆解本身正在成为一种新的工程能力。**

---

### 2. 上下文工程

Agent 的能力并不完全取决于模型。

同一个模型，在不同工程环境中的表现可能差异巨大。

影响 Agent 效率的因素包括：

```text
模型能力
×
上下文质量
×
工具能力
×
环境稳定性
×
验证机制
```

例如 Agent 是否能够：

- 理解项目目录；
- 获取架构说明；
- 找到相关代码；
- 查询日志；
- 启动开发环境；
- 调用浏览器；
- 执行测试；
- 获取 CI 结果。

这些能力决定了 Agent 能不能真正从「代码生成器」变成「软件工程 Agent」。

---

### 3. 结果评审

当代码生成速度提高一个数量级之后，新的瓶颈很可能变成：

**人类 Review 的速度。**

如果一天只能认真 Review 5 个任务，那么即使同时运行 50 个 Agent，也没有意义。

因此未来的 Review 也需要从：

```text
逐行阅读 Diff
```

逐渐转向：

```text
任务目标
  ↓
运行结果
  ↓
测试结果
  ↓
截图 / 视频 / 日志
  ↓
关键 Diff
```

对于前端功能，甚至可以让 Agent 直接提供：

- 页面截图；
- 操作录像；
- Preview URL；
- Console 日志；
- 测试报告。

**Artifact-first Review（工件优先评审）**可能会比单纯阅读代码 Diff 更适合 Agent 时代。

---

## 三、真正的瓶颈可能不是模型，而是工程体系

Agent 数量增加之后，一些过去可以容忍的工程问题会被迅速放大。

例如一个测试有 2% 的概率随机失败。

对于一个开发者来说：

```text
失败 → 再跑一次
```

可能只是几十秒的小问题。

但如果每天有数百次 Agent 自动运行测试，这个问题就会变成大量：

- 无效重试；
- Agent 错误判断；
- 任务失败；
- 计算资源浪费；
- 人工介入。

因此过去被称为「工程卫生」的东西，在 Agent 时代会直接变成生产效率。

包括：

- CI 稳定性；
- Flaky Test 治理；
- 环境一致性；
- 一键启动能力；
- 权限管理；
- 日志完整性；
- 自动化测试；
- 可恢复脚本；
- 可观测性。

可以把它理解成：

> **不稳定的工程体系，会把 Agent 变成高频失败放大器。**

模型越快、Agent 越多，这些问题反而会被放大得越严重。

---

## 四、多 Agent 并不意味着效率线性增长

很容易产生一个直觉：

```text
1 Agent = 1x
10 Agents = 10x
```

现实中通常不会如此。

因为并行 Agent 会带来新的问题：

```text
任务依赖
代码冲突
上下文重复
环境竞争
结果合并
Review 堆积
回归风险
```

假设两个 Agent 同时修改同一个核心模块：

```text
Agent A → 重构 UserService
Agent B → 给 UserService 增加缓存
```

两边单独看都可能正确，但最终合并时可能产生大量冲突。

因此，多 Agent 的关键不是「启动更多 Agent」，而是：

**如何把一个复杂问题切分成尽可能低耦合的任务图。**

例如：

```text
Epic
 │
 ├── Task A：Database
 │
 ├── Task B：Backend API
 │
 ├── Task C：Frontend
 │
 └── Task D：Tests
```

如果存在依赖，则进一步变成：

```text
Database
   ↓
Backend
   ↓
Frontend
   ↓
E2E Test
```

这其实已经非常接近传统的软件工程管理。

区别只是过去管理的是：

**Developer**

未来可能同时管理：

**Developer + Agent**

## 五、工程师真正需要升级的能力

AI 编程并不意味着「编程能力不重要了」。

相反，随着实现成本下降，一些过去容易被编码工作掩盖的能力会变得更加重要。

### 系统设计

你需要判断：

- 模块应该如何拆分；
- 数据应该如何流动；
- 哪些地方应该抽象；
- 哪些地方不应该抽象；
- 哪些技术债可以接受。

Agent 可以实现一个方案，但「应该实现什么方案」仍然需要工程判断。

### 问题拆解

一个模糊需求：

```text
把编辑器性能优化一下
```

可能需要被拆成：

```text
性能 Profiling
      ↓
确定瓶颈
      ↓
渲染优化
      ↓
状态管理优化
      ↓
资源加载优化
      ↓
Benchmark
```

其中每一步都可以进一步交给不同 Agent。

所以未来工程师的一项核心能力可能是：

> **把复杂问题转换成 Agent 可以并行执行的任务图。**

### 验收标准

如果没有明确验收标准，Agent 很容易得到一个：

> 看起来能运行。

的结果。

好的任务应该提前定义：

```text
功能正确
性能达标
测试通过
无明显回归
边界条件覆盖
代码可维护
```

甚至进一步变成自动化检查。

当验收标准能够机器执行时，Agent 的自治程度才能真正提高。

## 六、团队可以怎么开始？

没有必要一开始就构建几十个 Agent 的复杂系统。

更现实的路径是逐步提高自治程度。

### Stage 1：Agent 辅助

```text
Human
  ↓
Agent
  ↓
Human Review
```

先让 Agent 承担明确的小任务。

### Stage 2：Agent 完整完成任务

让 Agent 自己：

```text
理解
→ 修改
→ 测试
→ 修复
→ 输出结果
```

减少开发者中途介入。

### Stage 3：并行 Agent

同时运行：

```text
Agent A
Agent B
Agent C
```

开发者集中处理 Review。

### Stage 4：Agent Pipeline

进一步形成：

```text
Issue
 ↓
Planner Agent
 ↓
Implementation Agent
 ↓
Test Agent
 ↓
Review Agent
 ↓
Human Approval
```

到了这个阶段，软件开发已经非常接近一条自动化生产流水线。

---

## 七、从「写代码」到「设计生产系统」

过去我们优化的是：

```text
一个工程师写代码的速度
```

AI Coding Agent 出现之后，我们开始优化：

```text
一个工程师 + 一个 Agent
```

而第三个时代真正值得关注的，是：

```text
一个工程师
+
多个 Agent
+
自动化工程体系
```

最终的软件开发工作流可能越来越接近：

```text
            Human
              │
      ┌───────┴───────┐
      │ Problem Design │
      └───────┬───────┘
              ↓
          Task Graph
              ↓
    ┌─────────┼─────────┐
    ↓         ↓         ↓
 Agent A   Agent B   Agent C
    │         │         │
    └─────────┼─────────┘
              ↓
          Artifacts
              ↓
      Automated Checks
              ↓
         Human Review
              ↓
            Merge
```

这时候，工程师真正设计的已经不只是软件本身。

**还包括「软件是如何被生产出来的」。**

---

## 结语

AI 编程最值得关注的变化，并不是「模型能不能再多写一点代码」。

真正的变化是软件开发的抽象层级正在上移：

```text
写代码
  ↓
描述代码
  ↓
描述任务
  ↓
设计任务系统
  ↓
管理软件生产过程
```

代码仍然重要，但「亲自敲出代码」可能不再是工程师最主要的产出方式。

未来工程师之间的效率差距，也可能不再主要来自谁写代码更快，而来自：

**谁能更准确地定义问题、更合理地拆分任务、更有效地组织 Agent，以及建立一套能够自动验证结果的工程体系。**

从这个角度看，AI 软件开发的第三个时代并不是简单的「更强 Coding Agent」。

它更像是一次软件生产方式的变化：

> **从 Human-in-the-loop Coding，逐渐走向 Human-on-the-loop Software Engineering。**
